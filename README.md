# Pipeline

> Умный desktop-индикатор для CI/CD: показывает только важное, ведёт прямо к упавшей job и помогает быстрее понять, что сломалось.

Pipeline — это не замена GitLab, GitHub Actions или Jenkins.  
Это слой поверх них, который убирает постоянную необходимость открывать пять вкладок, проверять статусы руками и продираться через огромные CI-логи.

## Зачем это существует

Когда у разработчика несколько репозиториев и несколько CI-провайдеров, пайплайны превращаются в фоновый шум:

- где-то упал pipeline;
- где-то зависла job;
- где-то деплой ждёт ручного действия;
- где-то тесты красные, но причина спрятана в 10 000 строк логов.

Обычный workflow выглядит так:

1. открыть GitLab;
2. открыть GitHub;
3. найти нужный репозиторий;
4. найти нужный pipeline;
5. открыть job;
6. проскроллить лог;
7. понять, что ошибка была внизу после тонны `npm install`.

Pipeline меняет модель:

> Ты не проверяешь CI. CI сам приходит к тебе, когда нужно внимание.

## Core idea

Pipeline работает как умный inbox для CI/CD.

Он не заставляет держать открытыми вкладки с GitLab и GitHub.  
Он следит за выбранными репозиториями и показывает только события, на которые нужно реагировать.

## Для кого

Pipeline делается для разработчиков, которые:

- ведут несколько своих и рабочих репозиториев;
- используют GitLab CI и/или GitHub Actions;
- не хотят постоянно открывать web-интерфейсы CI;
- хотят быстро понимать, что именно сломалось;
- не являются dedicated DevOps-инженерами, но вынуждены регулярно чинить pipelines.

Это инструмент для backend/fullstack/indie-разработчиков, которым CI мешает работать, но без CI уже нельзя.

## Чем Pipeline НЕ является

Pipeline не пытается стать новым GitLab.

Он не делает:

- git hosting;
- code review;
- issues;
- собственную CI-инфраструктуру;
- собственные runners;
- enterprise DevOps-платформу.

Pipeline — это маленький, быстрый и сфокусированный клиент для контроля и дебага CI.

## Главные боли

### 1. Слишком много репозиториев

Когда проектов много, CI размазан по разным страницам, вкладкам и провайдерам.

Pipeline собирает их в одно место.

### 2. CI требует постоянной ручной проверки

Разработчик сам идёт проверять, не упал ли pipeline.

Pipeline переворачивает модель: если всё нормально — он молчит. Если что-то требует внимания — он сообщает.

### 3. Логи слишком шумные

Настоящая ошибка часто спрятана среди установки зависимостей, Docker build output, warning-ов и повторяющегося мусора.

Pipeline должен показывать не весь лог как простыню, а главное место поломки.

### 4. Слишком много кликов до причины ошибки

В web-интерфейсе нужно пройти несколько экранов, чтобы попасть в нужную job.

Pipeline должен вести сразу туда, где проблема.

## MVP

Первая версия должна решать одну задачу:

> Быстро понять, что в CI требует внимания.

### 1. Project watcher

Пользователь добавляет репозитории из GitLab и GitHub.

Pipeline периодически получает статусы последних pipelines/workflow runs и показывает общее состояние:

- failed;
- running;
- success;
- manual action required;
- canceled/skipped.

### 2. Smart CI inbox

Главный экран — не вкладки по проектам, а список событий по важности.

Пример:

```text
Failed
  neegde / main / test
  backend-api / dev / docker-build

Running
  thatsoundbot / main / deploy

Recent success
  pipeline / feature/ui
```

Важное всегда сверху. Успешное не шумит.

### 3. Menu bar / tray status

Pipeline живёт в фоне и показывает текущее состояние CI:

- зелёный — всё спокойно;
- жёлтый — что-то выполняется;
- красный — есть упавшие pipelines;
- серый — нет соединения или токен недействителен.

Клик по иконке открывает список актуальных проблем.

### 4. Jump to failure

Один клик по событию открывает:

- конкретный pipeline;
- конкретную job;
- лог с местом ошибки.

На старте можно открывать web-страницу провайдера.  
Позже — показывать лог внутри Pipeline.

### 5. Basic log viewer

Минимальный просмотр логов внутри приложения:

- загрузка job log;
- поиск по логу;
- подсветка ошибок;
- сворачивание очевидного шума;
- переход к строкам с `error`, `failed`, `exception`, `traceback`, `fatal`.

## Не-MVP

Эти фичи важны, но не нужны в первой версии:

- локальный запуск CI;
- replay упавшей job локально;
- AI fixer;
- YAML editor;
- visual pipeline editor;
- cost dashboard;
- flake tracker;
- multi-provider analytics;
- Jenkins/Bitbucket support.

Они могут появиться позже, если базовый продукт окажется полезным.

## Roadmap

### v0.1 — Local-first CI monitor

- авторизация через personal access token;
- поддержка GitLab;
- добавление репозиториев вручную;
- получение последних pipelines;
- tray/menu-bar индикатор;
- список failed/running/success;
- переход в web-интерфейс провайдера.

### v0.2 — GitHub Actions support

- подключение GitHub;
- единая модель repository / pipeline / job;
- общий inbox для GitLab и GitHub;
- фильтры по проектам и веткам.

### v0.3 — Built-in log viewer

- просмотр логов внутри приложения;
- поиск;
- error highlighting;
- авто-сворачивание шумных секций;
- быстрый переход к вероятной причине падения.

### v0.4 — Smarter signals

- уведомления только о важных событиях;
- mute для репозитория/ветки;
- настройка watched branches;
- группировка повторяющихся падений;
- определение зависших jobs.

### v1.0 — CI command center for developers

- стабильная поддержка GitLab и GitHub Actions;
- быстрый inbox;
- tray/menu-bar режим;
- smart log viewer;
- быстрые действия: retry, cancel, open commit, open MR/PR;
- локальное хранение настроек.

## Принципы продукта

### Меньше шума

Если всё зелёное — Pipeline не должен мешать.

### Один клик до проблемы

Пользователь не должен проходить пять экранов, чтобы понять причину падения.

### Не заменять провайдера

GitLab и GitHub уже умеют запускать CI.  
Pipeline должен делать работу с ними быстрее и спокойнее.

### Local-first

Токены, настройки и история по возможности хранятся локально.

### Маленький scope

Pipeline должен быть хорош в одном: показывать, что с CI прямо сейчас.

## Почему не просто GitLab/GitHub UI?

Потому что web-интерфейсы провайдеров хороши как универсальные панели управления, но неудобны как ежедневный рабочий индикатор.

Pipeline не пытается повторить весь web UI.  
Он берёт только самый частый сценарий:

> Что у меня сейчас сломалось и куда нажать, чтобы это починить?

## Почему не просто Slack/email notifications?

Потому что уведомление говорит только факт:

> pipeline failed

Pipeline должен давать контекст:

- какой репозиторий;
- какая ветка;
- какая job;
- где ошибка;
- что можно сделать дальше.

## Возможные будущие фичи

Если MVP подтвердит ценность, дальше можно развивать Pipeline в сторону дебага:

- local job replay;
- сравнение двух запусков;
- анализ отличий env/cache/artifacts;
- определение flaky tests;
- AI explanation для упавшего лога;
- рекомендации по ускорению pipeline;
- локальный dry-run перед push.

## Технический стек

Планируемый стек:

- Tauri для desktop-клиента;
- TypeScript для UI;
- Rust backend layer;
- SQLite для локального хранения;
- GitLab API;
- GitHub REST/GraphQL API.

## Статус

Проект находится на стадии раннего прототипа.

Сначала цель — сделать инструмент, которым автор сам будет пользоваться каждый день.  
Если он реально уменьшит количество открытых вкладок и ускорит реакцию на падения CI, проект имеет смысл развивать дальше.
